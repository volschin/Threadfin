# Go 1.27 Modernization Design

**Status:** Approved for implementation planning  
**Date:** 2026-08-26  
**Target:** First-party Go code in the repository root and `src/`; `vendor/` is excluded

## Context

Threadfin's source predates Go 1.22, but the project now declares `go 1.27.0`. CI reads the version from `go.mod`, both Docker builders use Go 1.27, and the README requires Go 1.27 or newer. Release builds target Linux (`amd64`, `arm64`, `arm`), FreeBSD (`amd64`, `arm`), macOS (`amd64`, `arm64`), and Windows (`amd64`).

An audit of 56 first-party Go files (16,543 lines) found useful Go 1.22–1.27 modernization opportunities. A full `go fix -diff -mod=vendor ./...` preview produced approximately 1.2 MB of changes, dominated by low-value `interface{}` to `any` churn. This design therefore uses reviewed, focused changes instead of applying the complete modernizer output.

Go 1.27 already provides automatic runtime gains without source changes: Swiss-table maps, the Green Tea garbage collector, size-specialized small allocations, and the v2-backed `encoding/json` implementation. The modernization must not claim those automatic gains as results of source edits.

## Goals

1. Adopt newer language and standard-library features where they make intent clearer, remove duplicated bookkeeping, or reduce measured allocations.
2. Establish deterministic benchmark coverage before changing performance-sensitive paths.
3. Improve high-volume parsing, serialization, and file serving only when benchmark evidence demonstrates a gain.
4. Replace duplicate ZIP extraction implementations with one directory-confined implementation based on `os.Root`.
5. Preserve supported platforms, external APIs, persisted formats, and existing error behavior unless a separately approved contract change says otherwise.
6. Keep commits small, reviewable, independently testable, and easy to revert.

## Non-goals

- Blanket replacement of `interface{}` with `any`.
- Direct migration to the stricter defaults of `encoding/json/v2`.
- Adoption of generic methods, generic aliases, custom iterators, or `unique` without an existing abstraction that they simplify.
- Concurrency redesign using `WaitGroup.Go`, atomics, `sync.OnceValue`, or `testing/synctest`; the audited code has no behavior-equivalent conversion sites.
- Method-specific HTTP routing changes without an approved request-method contract.
- Enabling h2c or changing supported HTTP protocols.
- Applying `omitzero` or other serialization-tag changes.
- Treating runtime/toolchain improvements as evidence that a source refactor improved performance.

## Design Principles

### Reviewed modernizers only

Each `go fix` analyzer is previewed independently. Only findings with clear behavior equivalence are accepted. Analyzer groups are implemented in separate commits or small related groups so reviews can attribute each change to one mechanism.

### Evidence before performance claims

Performance-sensitive production changes require a baseline and an after measurement using deterministic `testing.B.Loop` benchmarks. Results include `ns/op`, `B/op`, and `allocs/op`, collected with ten samples and compared with `benchstat`. Shared-runner wall-clock values remain informational rather than merge gates.

### Preserve contracts before improving internals

Tests establish current observable behavior before replacing parsers, serializers, HTTP paths, or filesystem operations. This includes output ordering, JSON compatibility, XML semantic equivalence, HTTP status/header behavior, archive overwrite rules, and platform-specific paths.

### Prefer standard boundaries over project-local copies

New shared code is introduced only when it replaces duplicated behavior with one focused boundary. The archive extractor is the main case: both callers need the same containment, permissions, cleanup, and overwrite policy.

## Workstream 1: Safe Language and API Modernization

Apply the following reviewed updates:

- Replace boolean-only `errors.As` targets with `errors.AsType` in production and tests.
- Use integer range for simple finite counting loops where the bound is not mutated.
- Use `reflect.Value.Fields` instead of manual `NumField`/`Field(i)` iteration.
- Use `slices.Index` for manual comparable-value index helpers and remove duplicate helpers.
- Use `slices.DeleteFunc` for stable one-pass filtering in the small M3U parser.
- Use `slices.Sorted(maps.Keys(...))` where code manually collects and sorts map keys.
- Use `slices.SortFunc` with a shared typed channel-number comparator where two index-based comparators duplicate policy.
- Use the built-in `max` for an ordinary integer lower-bound clamp.
- Use `strings.CutLast` where paired `LastIndex` calls express a final-delimiter parse.

The following modernizer suggestions are explicitly excluded:

- `any` across the codebase because it is broad syntax churn without behavioral or performance value.
- `slices.Backward` in loops that mutate the traversed slice; readability and equivalence are not clear enough.
- `clear` where replacing a map currently changes identity or releases capacity.
- `slices.Clone` where nil versus non-nil empty slices can affect serialized state.
- Broad `slices.Sort` spelling changes without a maintenance benefit.

### Verification

Run focused table tests for each changed helper or policy, followed by the complete test and cross-build matrix. No performance claim is attached to purely syntactic changes.

## Workstream 2: Benchmark Foundation

Add colocated benchmark files using `testing.B.Loop` for:

1. Normal M3U parsing at 1 MiB, 5 MiB, and 10 MiB.
2. Large M3U parsing at 1,000, 10,000, and 100,000 entries.
3. Filter condition evaluation with early match, late match, no match, empty elements, and repeated separators.
4. XMLTV generation with representative channel/program counts, including a 100-channel/10,000-program case.
5. Segment transfer with 188 KiB, 2 MiB, and 10 MiB inputs.
6. Cached image delivery with 32 KiB and 1 MiB files.
7. API/update JSON decoding with small and large payloads.
8. Internal map-to-JSON conversion with representative channel/configuration values.
9. Argon2 hash-string serialization measured separately from Argon2 key derivation.

Benchmark setup occurs outside `for b.Loop()`. Fixtures are deterministic and avoid full server initialization where narrower helpers are sufficient. CI must compile and may report benchmarks, but it does not reject changes based on shared-runner timing variance. Deterministic allocation limits may be added after stable baselines exist.

## Workstream 3: Measured Parsing and Collection Improvements

Candidates are implemented one at a time and retained only when measurements improve without contract changes.

### Lazy splitting

- Replace `strings.Split` with `strings.SplitSeq` in filter evaluation to remove a temporary slice and preserve early return.
- Replace the normal-size M3U parser's whole-playlist section slice with `strings.SplitSeq`, preserving unconditional preamble skipping and delimiter behavior.
- Consider `strings.SplitSeq` for other allocation-sensitive loops only when they do not need random access or an awkward manual index.

### Large M3U parser

Replace the scanner/builder/rescan pipeline with direct record processing over the original input. The parser passes the `#EXTINF` line and URL directly to metadata parsing rather than constructing and rescanning a channel string. Any use of `bytes.Lines` or `bytes.SplitSeq` must preserve:

- CRLF handling;
- comment lines between metadata and URL;
- final unterminated lines;
- output ordering;
- malformed-input behavior;
- the current line-size policy or an explicitly tested replacement.

The new path must be compared against the existing output on a compatibility corpus before the old implementation is removed.

### Encoding buffers

Use `base64.Encoding.AppendEncode` to build Argon2 strings in one destination buffer. The serialization benchmark is isolated from key derivation so allocation changes remain visible. Output must remain byte-identical.

## Workstream 4: Measured Serialization and Streaming

### JSON

Separate human-readable persisted JSON from compact wire/internal JSON:

- Persisted configuration files retain `MarshalIndent`.
- HTTP responses and internal conversions use compact bytes or an encoder when whitespace is not contractual.
- API and updater request/response decoding may use `encoding/json/v2.UnmarshalRead` with `json.DefaultOptionsV1()` to avoid body-sized intermediate buffers while preserving v1 semantics.

Compatibility tests cover duplicate names, invalid UTF-8, case-insensitive field matching, trailing data, empty bodies, reader failures, nil map/slice behavior, and existing error handling. Direct v2 defaults are not used.

### XML

Replace per-channel and per-program `xml.MarshalIndent` allocations with one reusable `xml.Encoder` over the existing buffered writer. Flush and close errors remain observable. Semantic equivalence is verified by unmarshalling old and new output; byte-for-byte formatting is compared separately before deciding whether whitespace is contractual.

Generating plain and gzip XMLTV in one pass is a separate commit. It may use `io.MultiWriter` only with temporary files, explicit close ordering, cleanup, and atomic publication so one failed destination cannot publish a partial accepted artifact.

### Segment and image delivery

- Replace whole-file image reads with a streaming path only after tests establish current status, content type, range, conditional request, and missing-file behavior.
- Replace whole-segment buffering with a small prefix sufficient for content-type detection plus streaming of the complete input.

Segment streaming changes failure timing: a read error can occur after headers or bytes have been sent. Tests must cover injected mid-read failures, byte identity, close errors, and partial-write behavior. The change lands only if this contract is accepted by existing handler semantics and allocation measurements justify it.

## Workstream 5: Directory-Confined Archive Extraction

Create `src/internal/archive` with one extractor used by backup restore and updater extraction.

The extractor:

1. Creates or validates the target directory.
2. Opens it with `os.OpenRoot`.
3. Converts canonical ZIP slash paths through `path.Clean` and `filepath.Localize`.
4. Rejects absolute, non-local, traversal, and invalid platform paths with explicit errors.
5. Creates directories and files through `os.Root` methods only.
6. Preserves the approved overwrite and permission policy.
7. Closes archive entries and output files promptly and joins relevant close/copy errors.
8. Removes incomplete output according to the caller's publication policy.

Tests cover nested files, archives without explicit directory entries, overwrites, modes, `../`, absolute paths, backslashes, pre-existing symlink escapes, concurrent symlink changes where testable, Windows junction/reparse behavior, and cleanup after failure. Native or cross-platform tests are required where filesystem semantics cannot be simulated reliably.

## Workstream 6: HTTP Routing and Origin Protection

The stream route may move from a manual `RequestURI` prefix strip to a ServeMux wildcard and `Request.PathValue`. Contract tests first capture:

- normal hexadecimal IDs;
- empty and nested suffixes;
- escaped paths;
- query strings;
- trailing slash behavior;
- GET, HEAD, POST, and unknown IDs.

The route migration must preserve current query and escaping semantics or document an approved change.

`http.CrossOriginProtection` is not enabled as part of the automatic modernization. It requires a separate trusted-origin and reverse-proxy contract, including Host/Origin rewriting and legitimate cross-origin browser clients. It remains a follow-up hardening decision.

## Workstream 7: PGO Pilot

PGO is a final research gate, not a default build change.

- Pilot only on Linux/amd64.
- Use a production-shaped workload covering large playlist import, XEPG generation, and concurrent streaming.
- Do not derive the profile solely from unit tests or microbenchmarks.
- Compare identical `-pgo=off` and `-pgo=<profile>` builds.
- Record throughput, CPU, p95 latency, RSS, allocations/GC metrics, binary size, and build reproducibility.
- Document profile provenance and refresh policy.
- Do not commit a profile, expose a profiling endpoint, or change release builds unless measurements show a repeatable gain and operational review approves the capture mechanism.

If no representative profile can be produced, this workstream ends with no build change.

## Error Handling and Failure Semantics

Modernization must preserve operational errors rather than suppress them. Streaming and encoder changes explicitly handle copy, flush, close, and publication errors. Multi-output generation uses temporary outputs and atomic publication to avoid accepting partial artifacts. Archive errors identify the rejected entry and containment reason without leaking unrelated filesystem details.

Mechanical changes such as `errors.AsType` preserve matching behavior. JSON streaming keeps v1 semantics through `json.DefaultOptionsV1()`. Any difference in error wording caused by Go 1.27's v2-backed implementation is treated as a compatibility concern only where tests or consumers rely on exact text.

## Verification Matrix

Every implementation phase runs:

```sh
go test -count=1 -mod=vendor ./...
go vet -mod=vendor ./...
git diff --check
```

Platform-sensitive phases also cross-build:

```sh
GOOS=linux GOARCH=amd64 go build -mod=vendor ./...
GOOS=linux GOARCH=arm64 go build -mod=vendor ./...
GOOS=freebsd GOARCH=amd64 go build -mod=vendor ./...
GOOS=freebsd GOARCH=arm go build -mod=vendor ./...
GOOS=darwin GOARCH=amd64 go build -mod=vendor ./...
GOOS=darwin GOARCH=arm64 go build -mod=vendor ./...
GOOS=windows GOARCH=amd64 go build -mod=vendor ./...
```

Release-equivalent binary commands remain covered by existing workflow validation. Filesystem behavior that depends on native Windows or Unix semantics requires native CI coverage or a documented limitation of cross-build-only verification.

Performance commits additionally run:

```sh
go test -mod=vendor -run='^$' -bench=. -benchmem -count=10 ./...
benchstat before.txt after.txt
```

## Commit and Rollout Strategy

1. Add behavior tests and benchmark foundation.
2. Apply low-risk modernizers in reviewed groups.
3. Apply collection and parser changes individually with benchmark evidence.
4. Apply JSON, XML, and streaming changes individually with contract tests and evidence.
5. Introduce the shared archive package and migrate one caller at a time.
6. Migrate the stream route after request-contract tests.
7. Run the PGO pilot without changing default builds; adopt only through a separate reviewed decision.

Each production behavior change has its own commit or narrowly related commit group. Benchmark-only commits precede the production changes they measure. Regressing or inconclusive performance candidates are reverted rather than justified by newer syntax.

## Success Criteria

- Full test, vet, formatting, and supported-platform build matrix passes.
- No unreviewed full-modernizer output lands.
- Mechanical changes reduce duplicated code or bookkeeping without changing behavior.
- Performance changes have reproducible benchmark evidence and no semantic regression.
- Both ZIP extraction callers use the same `os.Root`-confined implementation.
- Persisted JSON/XML and HTTP behavior remain compatible unless separately approved.
- PGO does not enter default builds without a representative profile and repeatable end-to-end gain.
